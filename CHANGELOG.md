## 3.4.0 (2026-11-27)

- added: `assertWithAI` and `assertNoDefectsWithAI` run for every driver (Android, iOS, tvOS, the browser, the computer device, Appium and cloud devices), in the executor on the daemon that owns the device, on a screenshot from the driver's own `Screenshot()`. A waterfall judges it: TypeSafe Jev (`jev-1.14.0`, the screenshot scaled into 280–1568 px, one noul question, passing at 0.7 or more and failing at 0.3 or less), then Claude Haiku, Sonnet and Opus 5.5 (pass or fail with confidence 0.7 or more stops it), else `unsure`. `budgetUsd` and `thresholds` (`jevPass`, `jevFail`, `haiku`, `sonnet`, `opus`) are new options on both. Every verdict is a successful step with `{verdict, confidence, model, escalations, observed, costUsd}` as its data, so the JS client resolves `fail` and `unsure` too; only a missing screenshot fails. `assertNoDefectsWithAI` asks the built-in assertion that the screen shows no visual defect. The cdp driver no longer answers them "not supported". See `docs/daemon/rest.md`.
- added: The AI checks' keys. A daemon's `config.json` takes an `ai` block, `{jevKeyFile, anthropicKeyFile, maxBudgetUsdPerCall}` (key files mode 0600, read at each check), whose keys it spends for every device it owns, capping a client's `budgetUsd` at `maxBudgetUsdPerCall`. A daemon without one spends keys its attach carried: `ai: {jevKey, anthropicKey}` in `POST /v1/devices/{id}/attach`, `attach --ai-keys-file FILE` (mode 0600) and JS `attach({ai})`. Attach keys stay in the session for the checks only, never in variables, reports, logs or answers, and a hub strips them from an attach it forwards. A stage without a key is skipped (`no-key`). See `docs/daemon/config.md`.
- added: `setStatusBar {mode: demo|live, time?, battery?}`: demo mode (9:41 and a full battery by default) through `simctl status_bar` on an iOS simulator and System UI demo mode on Android emulators and phones. A physical iPhone, iPad or Apple TV answers `UNSUPPORTED: status bar override on a physical iOS device` and changes nothing, as do the browser and the computer device; JS `supportsStatusBar(device)` tells ahead.
- added: `keyboardVisible` answers `{visible}` on Android (uiautomator2 and devicelab) and iOS (WebDriverAgent), and `pressKey escape` (or `esc`) sends `KEYCODE_ESCAPE` on both Android drivers.
- added: `pressKey` on iOS (WebDriverAgent) sends `up`, `down`, `left`, `right` (or `dpad_up`, `arrowUp`, …) and `escape` (or `esc`) as hardware keys with XCUITest's `typeKey`; a device before iOS or iPadOS 17, or a WebDriverAgent without the route, answers `UNSUPPORTED` naming the key. `tab`, `enter`, `delete` and `space` are typed into the focused field as before. The devicelab_ios driver answers `UNSUPPORTED` for any key it cannot send.
- added: Pointer gestures upstream Maestro has no command for. `hoverOn {selector or point, duration?}` moves the pointer onto an element (scrolled into view, at its `point:` or its centre) or a point without pressing, then waits `duration`: the browser's mouse and the computer device's `moveMouse` (a point only); Android and iOS answer `UNSUPPORTED` (a touch screen has no hover). `holdOn {selector or point, duration?}` presses, holds `duration` (1000 ms by default) and releases: `longPressOn` on an element and a timed press on a point, on every driver that has those. `dragPath {points, duration?, holdDuration?}` presses at the first of two or more points (`"x, y"` pixels or `"x%, y%"`), moves through each later one and releases at the last, the `duration` (1000 ms) shared among the legs by length: the browser's mouse (moves of at most 10 px), one W3C touch action on WebDriverAgent and uiautomator2, and `input motionevent` (Android 11 or later) on devicelab; any other driver answers `UNSUPPORTED`. The browser's `tapOn {point}` now reads `"x, y"` as pixels, and holds the press for `longPress` or a `duration`.
- added: `startSampler {kind: cpu|memory|frames, appId?, intervalMs?}` and `stopSampler {kind}` sample an app in the background and answer `{kind, unit, appId, intervalMs, durationMs, count, min, max, mean, samples}` on every platform: all three kinds on Android, cpu and memory on an iOS simulator; anything else is `UNSUPPORTED`. A session's end stops its samplers.
- added: `installApp` from a URL: `POST /v1/devices/{id}/apps` takes `url`, `headers` and `appId`, and the daemon that owns the device downloads the build itself, following redirects without forwarding `headers` or `Authorization`, and remembers each device's installed `ETag` per app (`<home>/installs.json`): a `304` or the same `ETag` answers `cached: true` without installing. CLI `installApp --url U --app-id ID [--headers-file F]` (a mode-0600 JSON object), JS `installApp({url, headers, appId})`. The fetching daemon downloads only from the hosts its `config.json` lists in `installApp.allowHosts`, and follows a redirect only to them or, over https, to a DigitalOcean Space (`*.digitaloceanspaces.com`); anything else is `FORBIDDEN`. Without the block a local caller may name any URL and a remote caller none.
- added: `clearState` on a physical iPhone or iPad after `installApp` from a URL: the device's own daemon keeps the build it last installed per device and app id (`<home>/builds/<device>/<appId>/`, beside the `ETag` record) and reinstalls it, when the attach gave no app file. Without a kept build it fails, naming `installApp`. A build counts as installed (`cached`) only while it is kept, and an uninstall forgets the `ETag` and the build.
- added: `config.json`'s `hubDevices[].capabilities`, any JSON value, returned byte for byte as `capabilities` in device listings, `GET /v1/devices/{id}`, lease, attach, boot and create answers, through every hub of the mesh. maestro-d gives it no meaning. A hub no longer re-encodes a peer's answers, so key order and number literals survive.
- added: `device create --platform android --hub NAME` is documented and tested, as iOS's was, and JS `createDevice({hub})` sends it.

## 3.3.0 (2026-11-23)

- added: Reservations: a hub lends a device for a window that starts later. `POST /v1/reservations` takes `device` or `select`, `startAt` (RFC 3339, at most the hub's `--reservation-lead` ahead, 24 hours by default), `clientTime` (the caller's clock, refused more than 60 s from the hub's with `reason: clock-skew`), `ttlSec` (at most the device's maximum, as for leases) and `holder`; its body is strict. The answer is a lease in the new `state` `scheduled` (every lease now carries `startsAt` and `state`), and device listings carry each device's `reservations`. No two leases on a device overlap in time: a lease, renew or reservation that would is `DEVICE_IN_USE` (with `nextStartsAt` for a reservation), so a lease taken now with the default 8-hour window is refused on a device reserved within 8 hours. Before its start a request under it is the new `LEASE_NOT_STARTED` (exit 5, 409); at the start the sweeper starts it (`lease.granted`, after `lease.scheduled` at the grant) with no connection waiting, and any client that has the id uses it. Cancel it with `DELETE /v1/leases/{lid}`; deleting its device ends it. A reservation boots, attaches and launches nothing, and takes no emulator or cloud device. The mesh routes the new route as it routes leases, forwarding every body key as sent; a hub that predates it answers "no route" (`reservations-unsupported` through the mesh). `hub status` reports `reservationLeadSec`; `Client.Reserve` in Go. See `docs/daemon/rest.md`.
- added: A hub keeps its reservations across a stop or a crash, in `<home>/hub/scheduled-leases.json` (`<home>/hub/daemons/<daemon>/…` for another daemon name), mode 0600, rewritten after every change to them. Starting, it reads them back under their own lease ids: one whose window is over is dropped, one whose start passed meanwhile starts at once with its own end, and an unreadable file is moved aside to `.bad`. Leases that had started still end with the hub. See `docs/daemon/hub.md`.
- added: `maestro-d reserve (--device ID | selector) --start-at TIME [--ttl D]` reserves a device for later (`--start-at` an RFC 3339 time or a duration from now, sent with this machine's clock) and records it in `leases.json`; `maestro-d claim --lease ID` takes a lease by its id on any machine (a reservation from its start, `LEASE_NOT_STARTED` before it), records it and attaches the device; `release --lease ID` ends one lease, and `release --device` now ends every lease this client holds on the device, reservations included. `leases.json` holds several leases per device, each with its `startsAt`: commands send the one that started last, else the reservation that starts first, `renew` without `--device` skips reservations, and `lease --device` never takes a reservation on file for a lease. `device list`'s LEASE column shows `next <holder> <start>` for a device with a reservation and no lease. See `docs/daemon/cli.md`.

See `docs/daemon/js.md`.
- added: Apps on cloud devices, and Device Farm without a device. `maestro-d install FILE --device df-…` (`POST /v1/devices/{id}/apps`, JS `installApp`) uploads the app to Device Farm, reusing an identical upload from the last 30 days, and installs it into the running session, answering once the device lists the app (Device Farm installs asynchronously; up to 120 s when the app id can be read); the device keeps its id, an attached device's WebDriver session is reopened so the next step sees the app, the install waits for a step in flight (`?wait=false`: `BUSY`) and holds the idle clock, and through a hub the file goes up under the lease. `uninstall` on a cloud device is `USAGE`. `maestro-d devicefarm account|apps|upload|sessions` (`GET /v1/providers/devicefarm/account`, `GET|POST …/apps`, `GET …/sessions`; JS `md.devicefarm`) reads the trial minutes, lists and uploads apps and lists sessions; on a hub they are answered by the hub with the credentials (`--hub` names one), and a remote `upload` is `FORBIDDEN`, with the install hint. `docs/maestro-runner.md`'s links now resolve from `docs/`.

## 3.2.0 (2026-11-20)

- added: `assertScreenshot` takes three options for unattended runs. `mask` lists selectors whose elements are left out of the comparison on both images, on every driver including the web one; a mask element that is missing or has empty bounds fails the step, and `mask` cannot be combined with `cropOn`. `requireBaseline` fails with `BASELINE_MISSING` instead of creating a missing reference from the capture; with `--update-screenshots` the missing reference is written, so a suite that always sets `requireBaseline` records new baselines that way. `captureOut` is where the settled frame is always written, whether the comparison passes, fails or has no baseline; it may not name the step's reference or its diff. `captureOut` is an output, like `takeScreenshot`'s path: a remote caller's lands in the call's outputs directory, a client targeting a hub fetches it back, and `maestro-d pack --flow` refuses one that is absolute or leaves the flow's directory. See `docs/daemon/rest.md`.
- added: With `requireBaseline` or `captureOut` set, every `assertScreenshot` result's `data`, passing or failing, holds `code`, `matchPercentage`, `differingPixels`, `totalPixels`, `diffPath` and `capturePath`, so a harness need not parse the message. `code` is `BASELINE_MISSING` for a missing reference, `SIZE_MISMATCH` for a screen that changed size (which always fails; it is compared on a common canvas only for its diff and numbers), `BASELINE_CREATED` or `BASELINE_UPDATED` for a step that wrote its reference rather than comparing (its match figures are zero), and absent for a comparison.
- added: `GET /v1/devices/{id}/state` reports `appState` and `foregroundApp` (the bundle or package id in front) on every real driver, within a two-second limit after which the two fields are absent and the rest still answers. `appState` is `foreground` when the session's app (the one last launched) is in front and `background` when another app is. The Android drivers ask adb, Appium asks its server, and WDA, which does not know the session's app, reports only `foregroundApp`. `devicelab_ios` reads the attached app's own state through the runner's `appState` command, which never activates the app, so a crashed app reads `not_running` rather than being relaunched.
- changed: **A web `tapOn` on an element something covers now fails** with "blocked by overlay", naming what covers it, as a tap inside an iframe already did. It used to succeed through the JS `click()` fallback, which reached the element whatever lay over it; a flow that tapped through a cookie banner or sticky header must now dismiss it first. Rod's wait for the element to be interactable and enabled is bounded at 5 s (it had no deadline, so a covered element held the command and the daemon), and for every selector it waits that long for an overlay that is leaving, such as a closing dialog or a toast; an element in the clear whose wait runs out, or any other error before the press, still falls back to the JS click. A press or release that fails fails the tap with its error, since it may have reached the page, rather than clicking a second time.
- changed: Headless Chrome on Linux reports a mouse, a fine pointer that hovers, as a Mac's does, where it used to report a touch screen: pages no longer switch to their touch forms (a chat composer that stops sending on Enter, menus that open their touch layouts).
- fixed: Browser sessions release unused network request history and avoid caching downloaded responses, reducing memory use while preserving navigation waits, request matching and network emulation.

## 3.1.0 (2026-11-19)

- added: The core of live screen streaming and recording. A device's own H.264 video and its AAC or LPCM audio are wrapped in fragmented MP4 as they arrive, with no decoding or re-encoding on the host: a pure-Go muxer writes `avc3` video (parameter sets in band, so a rotation needs no new init segment), `mp4a` AAC and LPCM as the source delivers it, `ipcm` for integer samples and `fpcm` for floating point, one fragment per sample. One capture session per device feeds every viewer and recorder: a viewer or recording that joins late starts at the moment it joins (the frames since the latest keyframe arrive first, a millisecond apart, so the picture is whole at once and nothing from before the join plays), a viewer that falls behind is dropped rather than slowing the device, and a device that starts capturing on demand stops 10 s after its last viewer leaves. Recordings end with their duration and a seek index (`mehd`, `mfra`), so a browser's `<video>` knows their length and can seek. A requested frame rate is 3–60 fps, 15 by default.
- added: Live screen streams. `GET /v1/devices/{id}/stream?fps=&audio=` answers an attached device's screen as fragmented MP4 (chunked, each fragment flushed as it is made) until the client leaves, while steps keep running on the device; `X-Maestro-Fps`, `X-Maestro-Audio` and `X-Maestro-Codecs` describe it. `maestro-d stream [--fps N] [--audio] [--duration S] [-o FILE|-]` writes it to a file or stdout and stops on Ctrl-C or `--duration` with exit 0 and a file that plays; `device.stream({fps, audio, signal})` in the JavaScript library and `Client.Stream` in Go return it too. Streams pass through the hub mesh under the device's lease, on bulk links that do not count against a peer's four transfers. The mock driver (an embedded clip), Android devices and emulators, and physical iPhones and iPads on a macOS host stream. See `docs/daemon/streaming.md`.
- added: A browser viewer. `GET /v1/viewer#device=<id>&token=<token>` is a page that plays a device's stream in Chrome, Safari or Edge: muted autoplay with an Unmute button, kept at the live edge, a status line with the size, frame rate, frame count and audio state, and a reconnect every 3 s. It is served without the bearer token (on a daemon and on a hub), at exactly that path, and reads the token from its URL fragment, which never reaches a server.
- added: Physical iPhones and iPads stream and record on a macOS host. Attaching one over USB starts its screen capture through Apple's QuickTime screen-capture channel before WebDriverAgent (starting it re-enumerates the device on USB), and keeps it running until the device is detached: streams, the viewer, `--record`/`--video` and the `startRecording`/`stopRecording` steps all read the device's own H.264 at about 60 fps (`X-Maestro-Fps: device`) with its LPCM audio as the device delivers it (`ipcm` for 16-bit integer samples, `fpcm` for 32-bit float). The capture runs in a small helper app, `MaestroDCapture.app`, that maestro-d builds with `xcrun swiftc` on first use, signs with the Mac's Apple Development identity (`MAESTRO_D_CAPTURE_SIGN_IDENTITY` to choose another) and runs once per maestro-d process; macOS asks once per Mac to let "MaestroDCapture" use the camera. A capture that fails never fails the attach: `device.capture` and `CAPTURE_UNAVAILABLE` say why (`camera-permission`, `no-capture-device`, `ambiguous-device-name`, `helper-failed`, `not-macos`), and a capture lost mid-attachment adds a re-attach hint to steps that then fail with a network error. Run one capture-enabled maestro-d process per Mac: the capture channel is a switch for the whole Mac, and other processes using USB iOS devices lose their connections when it turns on or off. `maestro-d test` captures only when the run records; the one-shot `screenshot` and `hierarchy` never do. Simulators keep `simctl` recording. See `docs/daemon/streaming.md`.
- added: `CAPTURE_UNAVAILABLE` (exit 4, HTTP 503) answers a stream of a device without screen capture, one whose capture failed, or one that sent no frames within 10 s; `details.reason` names why (`unsupported-platform`, `simulator`, `no-frames`, …). The `device.capture` event reports a device's capture state (`capturing`, `unavailable`, `lost`).
- changed: `startRecording` / `stopRecording` on a device with screen capture write into the report. The executor records the device's capture session itself: `startRecording: <name>` writes `recordings/<name>.mp4` in a daemon session's report directory (served by `GET …/artifacts`), or under the flow's assets in `maestro-d test`, and the step's `data` is that path. A directory in the name is dropped, `.mp4` is optional, and no name means `recording`; a second `startRecording` while one runs fails the step, and a recording left running is finalized when the flow, session or attachment ends. Drivers without capture keep their own handling. The mock driver now records (`--record` and the steps).
- changed: The Android recorder has no 3-minute cap, and records audio. Android devices and emulators (the `uiautomator2` and `devicelab` drivers) now capture their screen through a pinned scrcpy-server (5.0.1, shipped in `drivers/android/`), pushed over adb and started when a stream or recording needs it, stopped 10 s after the last one ends. `--record` / `--video` and the `startRecording` / `stopRecording` steps record through it on the host, for as long as the flow runs (screenrecord stopped at three minutes), with the device's AAC audio on Android 11 and later. The same capture serves live streams, the viewer and `maestro-d stream` on Android. **`startRecording` writes to the report directory:** it used to run `screenrecord` into `/sdcard/recording.mp4` (or the step's `path`) on the device and leave the file there; the file is now `recordings/<name>.mp4` beside the report, and the step's `data` names it. See `docs/daemon/streaming.md` for the Android limits (`FLAG_SECURE` screens capture black, audio on Android 11 needs the screen unlocked when capture starts, Android 11–12 audio capture mutes the speaker, Android 13 and later capture only apps that allow playback capture).
- fixed: A hub that is stopping turns peers that redial it away as stopping (503 `PEER_UNAVAILABLE` before the upgrade, and a going-away close for a link that races its shutdown), so they see it as stopped rather than down, and no link registers after its mesh has closed.
- fixed: `hub status` shows a peer's refusal as soon as `hub start` returns on it.

## 3.0.1 (2026-11-18)

- added: Every daemon sweeps its home half a minute after it starts and then hourly, and `maestro-d gc [--dry-run] [--json] [--include-build-cache]` runs the same sweep on demand. It deletes blobs unused for 24 hours (was 7 days, and only at daemon start), report directories idle for 3 days, orphaned Chrome profiles idle for a day, and the run directories of daemons gone for 7 days. It never removes the run directory of an installed hub service or one that still records simulators its daemon booted. `MAESTRO_D_HOUSEKEEPING_INTERVAL` overrides the hour.
- added: `discardReports` (`--discard-reports`, JS `discardReports`) deletes a session's report directory at detach.
- changed: Daemon sessions write `report.json` and `junit-report.xml` only, no `report.html` or `allure-results/`; `maestro-runner test` still writes every format. Detach removes the app copies and flow bundles a session unpacked into its report directory.
- changed: The Android drivers trace nothing by default. With `MAESTRO_D_ANDROID_TRACE=1` they write `client.log` into the session's report directory, truncated at 50 MB, with typed and pasted text redacted. Previously every request, typed text included, was appended to `/tmp/maestro-client.log` or `/tmp/devicelab-driver-client.log` without limit.
- fixed: iOS test runs no longer leave their result bundles behind. WebDriverAgent's session log grew in the build cache's `DerivedData/Logs/Test` for as long as WDA ran (one reached 2.1 GB); each run now writes its own result bundle and deletes it when it stops. The devicelab runner no longer makes a new folder under `~/Library/Developer/Xcode/DerivedData` for every run, and builds skip the unused index store.
- fixed: iOS runner build caches unused for 30 days are pruned (real-device builds only once this machine has compiled one for the same team since).
- fixed: A web session's temporary Chrome profile (about 22 MB) is deleted when the session closes, or when Chrome fails to start.
- changed: `BlobStore.Expire` is removed; the housekeeping sweep expires blobs.

## 3.0.0 (2026-11-18)

- added: Hubs: `maestro-d hub start` runs a daemon that shares this machine's devices with clients on the network and lends each device to one client at a time. Leases are fixed windows (`maestro-d lease`, `renew`, `release`; 8 hours by default, `--lease-max` for the hub or one device), using a device past its window fails `LEASE_EXPIRED`, and using one without a lease fails `LEASE_REQUIRED`. `--share-device` limits what the hub shares, `--token`/`--token-file` and `--tls-cert` secure it, and `hub service install` runs it as a macOS LaunchAgent.
- added: Hub mesh: hubs find each other with mDNS at launch, or link with `--peer`, and pass their peers on, so any hub lists and drives every hub's devices as `<id>@<hub>`. Device listings name each device's machine and addresses. A hub whose link is down fails its devices' requests `PEER_UNAVAILABLE` and relinks on its own.
- added: Physical Apple TVs: TVs paired with the Mac (over the network, never USB) are listed as `ios` devices of kind `tv`, found through `devicectl`. Attaching one builds and starts the tvOS WebDriverAgent over the CoreDevice tunnel; `pressKey up|down|left|right|select|menu|home|playPause` moves focus, and screenshots, assertions and the element tree work as on a phone. A hub shares a TV only when `--share-tv` names it, and a lease selector picks a TV only with `--kind tv` or its name.
- added: tvOS simulator sessions, and Siri Remote touchpad swipes (`swipe` by direction or remote-trackpad percentages) on tvOS simulators and, through a paired Companion connection, on physical TVs.
- added: `--target-hub=HOST[:PORT]` (or `MAESTRO_D_HUB`) on every command talks to a daemon or hub on another machine, with `--token` and `--ca` for its bearer token and TLS trust. Files a command references, `install` packages and `attach --app-file` apps are uploaded with the call (resumable, content-addressed, reused when the daemon already has them), and `get artifacts` fetches a run's outputs. The JavaScript library takes the same as `MaestroD.connect({hub, token, ca})`.
- added: Whole flows run on the device's host: `maestro-d run FILE --target-hub…` packs the flow with every file it references (`maestro-d pack --flow`), uploads the bundle and runs it there, `runScript`/`evalScript` included.
- added: `maestro-d device catalog|create|delete` (REST `GET /v1/catalog`, `POST /v1/devices`, `DELETE /v1/devices/{id}?delete=true`; JS `catalog()`, `createDevice()`, `deleteDevice()`) list the simulators and AVDs this machine can make, create an iOS simulator or Android AVD and boot it, and delete it again; only devices `device create` made are deleted.
- added: `pressKey LOCK` and `pressKey UNLOCK` on iOS set and verify the screen lock state (UNLOCK does not bypass a passcode), through the CLI, REST and the TypeScript library.
- added: `X-Maestro-Request-Id` on step requests: a client retries a dropped request with the same id and the daemon answers from its last outcomes, so a retried `inputText` types once.
- changed: Breaking: a daemon serving TCP treats every non-loopback caller as remote (and on a hub every TCP caller): `runShell` (unless `--allow-remote-shell`), host paths in any input or flow-file field, absolute or `..` output paths, `?cwd=`, and web, Appium or host-path attaches are refused with the new `FORBIDDEN` error (HTTP 403, exit 2). Relative outputs go under the session's `outputs/`. Remote sessions import only the daemon environment variables `--pass-env` names.
- changed: Breaking: the JavaScript library reports HTTP 401 as `USAGE` and HTTP 403 as `FORBIDDEN`; the error codes `FORBIDDEN`, `LEASE_REQUIRED`, `LEASE_EXPIRED`, `PEER_UNAVAILABLE`, `HUB_NAME_TAKEN` and `HUB_VERSION` are new, and every error response carries `X-Maestro-Error-Code`.
- changed: `device start` no longer needs `--platform` for an `avd:<name>` id.

## 2.0.0 (2026-11-09)

- added: Install with one command, without the repository. Each maestro-d release now carries a tarball per platform (`maestro-d-<version>-<os>-<arch>.tar.gz`: `bin/maestro-d`, `drivers/`, `LICENSE`), a `SHA256SUMS` over them, and `install.sh`. `curl -fsSL https://github.com/EdgeApp/maestro-d/releases/latest/download/install.sh | bash` installs the latest release into `~/.maestro-d`, checks its checksum and links `maestro-d` onto the PATH, without sudo; `--version`, `--prefix`, `--bin-dir` and `uninstall` cover the rest. An upgrade keeps `~/.maestro-d/cache`. A release tagged with a pre-release version (`maestro-d-v2.0.0-rc.1`) is a GitHub prerelease and never replaces the latest.
- fixed: iOS commands work while the app is in landscape. The viewport was measured once, at attach, and kept its portrait shape for the rest of the session, so in a landscape app an element right of the portrait width was refused as "bounds outside viewport", dropped from page-source matches, and unreachable by an absolute point, and percentage points landed in the wrong place. The WebDriverAgent driver now reads the viewport from `/window/size`, which follows the interface orientation, and reuses it for 500 ms; `setOrientation`, `launchApp` and a new session read it afresh. When WebDriverAgent cannot answer, the size measured at attach is used.
- fixed: `setOrientation` on iOS accepts `LANDSCAPE_LEFT`, `LANDSCAPE_RIGHT` and `UPSIDE_DOWN`. They were sent to WebDriverAgent as written, which it rejects; they are now translated to its own orientation keys. `PORTRAIT` and `LANDSCAPE` are unchanged.
- fixed: `takeScreenshot` with `cropOn` crops the right region in landscape on iOS. WebDriverAgent's screenshot is the portrait framebuffer, so the element's bounds are rotated into it by the rotation `/rotation` reports, and the crop is turned back so it comes out the way the element looks on screen, not sideways.
- fixed: Attaching to an iOS device that usbmuxd does not list works. A paired device on a USB-C network link (an iPad Pro, for one) is reachable only through CoreDevice, and the usbmuxd port forward failed with "device not found" after WebDriverAgent had started. The runner now falls back to a go-ios agent tunnel, then to the CoreDevice tunnel address `devicectl` reports, then to the address WebDriverAgent prints at startup, uses the first one that answers `/status`, and logs which path it used. The device's name and OS version come from `devicectl` in that case too. Each `devicectl` query gives up after 10 seconds, so a locked or still-pairing device fails the attach rather than hanging it, with `devicectl`'s reason in the error; attach asks `devicectl` once and reuses the answer for the device's name.
- fixed: `launchApp` with `stopApp: true` relaunches a running app on iOS. WebDriverAgent's launch only brings a running app forward, so the process survived; the app is now terminated first. Without `stopApp`, `launchApp` still brings a running app forward.
- fixed: Android `inputText` types emoji and other non-ASCII text when it falls back to key events. With `keyPress: true`, or when no focused field accepts the text, the UiAutomator2 driver sends key events, which the server builds from Android's virtual-keyboard key map; that map has no keys for emoji, accented letters or CJK, so the step failed with `KeyCharacterMap.getEvents is unable to synthesize KeyEvent sequence` after typing the text before the first such character. Those characters are now pasted (through the clipboard and `KEYCODE_PASTE`) in their place, and the rest is still typed as key events. Each paste is allowed to land before the clipboard is written again, and the clipboard is set back afterwards, so a later `pasteText` still gets a flow's `setClipboard` or `copyTextFrom` value: to what it held when that can be read, else to what the flow last put there (on Android 10 and later a value the app copied itself in between cannot be read, and the flow's value replaces it); with neither known, the clipboard is cleared rather than left holding a pasted fragment. Android 13 and later then show the clipboard overlay for a few seconds (top left), and it takes the taps aimed under it, so a step that taps there right after such an `inputText` should wait for it to go ([#2](https://github.com/EdgeApp/maestro-d/issues/2)).
- fixed: `pasteText` on Android pastes the clipboard. The clipboard read sent no content type, which the UiAutomator2 server needs, so it failed with a `NullPointerException`. Android 10 and later also hide the clipboard from UiAutomator2, so the read comes back empty there; `pasteText` then presses the paste key, which pastes whatever the device clipboard holds, including text the app copied itself. When the read works and the focused field refuses the text, it is typed the way `inputText` falls back to: key events, with what keys cannot type pasted. With nothing focused it still fails.
- fixed: An iOS attach without `teamId` uses the daemon's `MAESTRO_TEAM_ID` / `DEVELOPMENT_TEAM`. The CLI sends its own environment's team with every attach, but a REST or JavaScript attach (`MaestroD.connect` then `attach`) sends none, so WebDriverAgent was signed with no team and its physical-device build was looked up in `device-ios<version>-teamdefault`. The daemon now fills an empty `teamId` from its own environment, which a daemon spawned by `MaestroD.connect` inherits from the caller; a `teamId` in the request still wins ([#4](https://github.com/EdgeApp/maestro-d/issues/4)).
- fixed: WebDriverAgent builds on Xcode 27. The bundled WebDriverAgent project targets iOS 12.0, below the 15.0 that Xcode 27 builds for, so attaching a device or simulator failed with `WDA build failed` unless a build had been made by hand. When `xcodebuild -version` reports Xcode 27 or later, the build now passes `IPHONEOS_DEPLOYMENT_TARGET=15.0`; earlier Xcodes keep the project's targets and can still build for iOS 12–14 devices ([#4](https://github.com/EdgeApp/maestro-d/issues/4)).
- fixed: `addMedia` works on a physical iPhone with the default `wda` driver. It refused real devices and pointed at the `devicelab` driver, which cannot attach to one. The WebDriverAgent bundled with maestro-d now serves `/wda/addMedia`, which adds the photo or video on the device through PhotoKit, answering the one-time "add to Photos" permission alert itself; the driver sends each file there. Simulators still use `simctl addmedia`. The endpoint answers only the permission alert that names the runner and leaves every other alert alone. The runner asks for add-only access, but a WebDriverAgent built with Xcode 26 or earlier has no add-only usage description in its runner app, so iOS asks for the whole library instead: the runner then holds full Photos access, and `addMedia`'s result says so. A device's WebDriverAgent built before this change has no such route: the error names that build's directory to delete so the next attach rebuilds it, and says that a WebDriverAgent installed by `maestro-d wda update` never has it ([#3](https://github.com/EdgeApp/maestro-d/issues/3)).

Releases before 2.0.0 are upstream maestro-runner's: see [docs/upstream-changelog.md](docs/upstream-changelog.md).
